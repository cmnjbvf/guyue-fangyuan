# 软件区：把程序当作一种来源

> **什么时候读**：进来的是**可执行文件、安装包、APK、ASAR、固件或正在运行的程序**时读。拆完要变成自己的产品 → 接着读 `TAKE.md`。

文本有"正文"，程序没有。你手上只有一个 exe 或一个 APK，能读的只有字节。所以这一区的任务不是"理解"，是**先造出一份可读的材料**，再把它组织成可追溯的知识。

覆盖范围：原生可执行文件、动态库、APK / IPA、ASAR 与打包后的 JS 应用、.NET 程序集、固件、以及运行中的进程与页面。

取证工具是 REA（MCP 已注册）。REA 负责“看不见的东西怎么看见”，本路线负责“看见的东西怎么变成可用的知识”。两者是同一条流水线的两半，不重复对方的工作。

## 什么时候走这条路

先判断手上是什么，再决定要不要取证：

| 手上是什么 | 走哪条路 |
|---|---|
| 完整源码仓库 | **不走本路线**。直接读源码、目录结构、import 关系，常规代码阅读即可。REA 明确声明不用于此场景。 |
| 只有产物（exe/dll/so、APK、IPA、ASAR、JS bundle、固件、安装包） | 走本路线，用 REA 取证 |
| 产物 + 部分源码 | 以源码为主干，用产物补齐源码说不了的部分（打包后的实际行为、构建差异、被裁剪的模块） |
| 单个可执行文件、不知道是什么 | 先做身份确认，再选路由 |

判断标准只有一条：**要回答的问题能不能靠读现有源码得到**。能，就不上取证；不能，才取证。多做一个不需要的取证，比少做一个更浪费。

## 第一步：确认目标身份

不靠文件名、目录名、图标推断这是什么程序。先固定三样：

1. **绝对路径**
2. **SHA-256**（同名不同构建必须区分）
3. **体积与格式**（PE / ELF / Mach-O / ZIP / APK / ASAR / JS / 固件）

同一程序多次分析必须核对 SHA-256 一致，否则结论不能迁移。版本比较必须建立在两个已确认的产物上，不能拿“上周那个好像是 1.2 版”当基线。

## 按目标类型选第一把工具

REA 的硬规则是“先路由目标，再动手”。选错入口会导致后续全部无效：

| 目标 | 第一把工具 | 适合回答什么 |
|---|---|---|
| 原生可执行 / 动态库 | `open_binary`，需要元数据时 `binary_overview` | 文件结构、段、入口、导入导出 |
| ASAR 或已解包的 JS/Electron 树 | `analyze_javascript_application` | 模块图、入口、依赖关系 |
| 归档/包成员清单（ZIP/APK/IPA/MSIX/AppX/DMG） | `open_binary`（本地路径）；需要图与发现时 `inspect_artifact` | 里面装了什么、清单结构 |
| Android APK 的代码/类/方法/引用 | `inspect_android_package`，再按需用 Android 定点工具 | 组件声明、类结构、调用引用 |
| 托管 PE/CLI 程序集（.NET） | `inspect_managed_artifact` | 类型、方法、成员关系 |
| 固件镜像 | `inspect_firmware_regions`；要解包用 `extract_firmware`（新目录） | 分区、文件系统边界 |
| 离线 ELF 布局/符号/重定位/缓解措施 | `inspect_binary_layout` | 静态布局证据，不开反编译器 |
| Linux core dump | `inspect_recorded_crash` | 崩溃现场、线程与寄存器 |
| PE 资源树（图标组、版本信息） | `inspect_pe_resources` | 资源清单与原始负载范围 |
| 已打开的浏览器页面 | `list_browser_targets` | 页面内实际运行的代码 |
| 已打开的 Electron 运行时 | `list_electron_targets` | 打包应用的运行时视图 |
| 保留的 HAR / 抓包 | `inspect_web_network_capture` | 历史请求的实际形状 |
| EVM 字节码 | `inspect_evm_interface`（`raw` 或 `hex`） | 选择器与接口候选 |
| 大型任务跨多个功能/子系统 | 先 `binary_session` 查会话与可用性，再按上表进入 | 复用既有分析，避免重复开会话 |

拿不准目标形态时，先用 `binary_session` 查 `result.tool_availability`，看哪个操作在当前目标与主机上可用，不要硬调一个未广告的工具。

## 程序的“正文”是证据

文本资料的证据是字符区间 `[start,end)` 加逐字 `quote`。程序资料的证据是可定位的坐标，按来源类型取不同字段：

| 类型 | 定位字段 |
|---|---|
| 函数/过程 | 规范地址（如 `0x1400012A0`）、所属产物 SHA-256 |
| 模块/文件 | 包内路径、成员出现路径 |
| 字节/数据 | 文件偏移或虚拟地址，配 `address_to_file_offset` 换算 |
| 字符串 | 字符串表条目与引用点 |
| 运行时 | 采集记录、场景 ID、时间点 |
| 工具结论 | REA 返回的 `evidence_id` |

**引用纪律**：任何结论必须能指回一个 `evidence_id` 或坐标。指不回去的，就不是证据，是印象。客户端可能截断过长结果，截断的预览不能当完整证据用——需要全量时走 `inspect_analysis_view` 分页视图，或用 `export_evidence_bundle` 导出到指定路径。

## 收据格式：复用批量清单，只换证据字段

`batch-processing.md` 的收据结构对齐本区：`evidence` 换成程序坐标，kind 用其五类词表（观察→`fact`、推断→`inference`、未知→`unknown`）。**注意：本区收据是概念模板，不走 digest_batch.py 校验**——脚本只认字符区间，程序地址会被拒；对账靠本区的来源锚点自查：

```json
{
  "chunk_id": "func@0x1400012A0",
  "disposition": "extracted",
  "reason": "启动路径上的配置加载逻辑",
  "claims": [{
    "id": "config-proxy-fallback",
    "statement": "启动时读取配置中的 proxy 字段，为空则走直连",
    "kind": "fact",
    "evidence": [{
      "type": "procedure",
      "address": "0x1400012A0",
      "artifact_sha256": "…",
      "evidence_id": "…"
    }],
    "conditions": ["仅当命令行未覆盖该配置时"],
    "exceptions": [],
    "uncertainties": ["代理连接失败后的回退路径未覆盖"]
  }]
}
```

这样做的原因：程序消化和文本消化最终要汇进同一个知识库，收据结构分叉会导致无法合并、无法对账。字段可以扩展，形状不要分裂。

## 取证顺序：摘要 → 定点 → 交叉验证

不要一上来全量反编译。REA 的默认姿势是 summary-first：

1. **先要摘要**。大目标（未知体积的 JS 应用、大型 ELF）用 `"detail": "summary"`，拿到模块/段/入口的整体形状。模块身份要分页看，单文件路径可能对应多个图节点。
2. **再定点钻取**。只在摘要留下的具体问题上下钻：`analyze_function`、`procedure_pseudo_code`、`search_strings`、`get_call_graph`、`trace_call_path`。每下钻一次都要对应清单里的一个问题。
3. **最后交叉验证**。静态结论需要运行证据时，才用 `capture_electron_scenario`、`observe_web_session`、`observe_native_calls` 这类被动观察；静态能回答的，不额外跑运行时。
4. **不重复同一个分析**。返回结果没变、输入没变，就不要重跑。要更多细节时用保留的 `parent_evidence_id` 做更小的视图。

## 三分纪律：观察 / 推断 / 未知

这是 REA 的硬性要求，也是本路线最容易塌的地方。每条主张必须落在三档之一：

| 档位 | 含义 | 写法 |
|---|---|---|
| **观察** | 工具直接返回的事实 | 附 `evidence_id` 或坐标（落盘映射为 `fact`） |
| **推断** | 由事实推出、未直接验证 | 明写“推断”，并写清依据哪几条事实（落盘映射为 `inference`） |
| **未知** | 当前证据不足 | 用 `record_unknown` 登记，写清还需什么权威或环境 |

三条禁令：

- **不把静态分析说成观察执行**。看到某个函数存在，不等于运行时调用了它。
- **不从文件名、字符串、布局推断行为**。这三样只能当线索，不能当结论。
- **不把对比结果当因果**。`compare_artifacts`、`compare_functions`、`find_changed_behavior` 给出的是差异候选，不是“因为这个所以变了”。比较还要求可比：同一 provider、完整且兼容的页集，否则“没有差异”这个结论不成立。

## 产出：程序理解报告

不套用知识卡格式。程序消化的交付物是一份能被后续工作直接使用的理解报告，结构如下：

1. **它是什么** — 身份（路径、SHA-256、格式、体积、版本线索）
2. **能力地图** — 它能做什么，按功能域列，每条带证据坐标
3. **关键行为链** — 挑 3–5 条最重要的路径，从入口讲到结果，中间每步有落点
4. **接口与契约** — 对外暴露的命令行、配置项、网络端点、文件格式
5. **依赖与运行条件** — 需要什么环境、什么外部资源
6. **风险与限制** — 掉签名/未校验、硬编码凭据、危险回退、明显的设计缺陷
7. **未覆盖清单** — 明确哪些没看、为什么没看、看了能多知道什么

如果用户的目标是“照着做一个”，在报告末尾单列一节：**可复现的最小实现要点**，把观察到的行为与设计选择分开写——观察到的照抄，设计的自己补，不许混。

## 覆盖与未覆盖

- 每轮结束，把开工时的疑问清单逐条标为：已答 / 部分答 / 未答。
- 明确写出搜索边界（看了哪些模块、跳过了哪些），边界内的“没有”才算数；边界外的“没有”是未知。
- 静态覆盖不等于行为覆盖。跑通功能不等于理解实现，理解实现也不等于能复现。
- 收尾：用 `close_binary` 关闭已打开的原生会话，不留悬挂分析库。

## 本机能力边界（当前实测）

这条必须写死，否则会去调一个根本跑不起来的能力：

- **`GHIDRA_INSTALL_DIR` 未设置，IDA 未安装，常见路径下都没有引擎。** 因此**原生二进制的反编译（伪代码）当前不可用**。`procedure_pseudo_code`、`analyze_function` 这类依赖反编译引擎的调用会失败。
- 现在**能直接做**的：包成员清单（`open_binary` / `inspect_artifact`）、JS/Electron 分析（`analyze_javascript_application`）、APK 结构与类（`inspect_android_package`）、.NET 程序集（`inspect_managed_artifact`）、PE 资源（`inspect_pe_resources`）、ELF 离线布局（`inspect_binary_layout`，需 pwntools）、core dump（`inspect_recorded_crash`）。
- 需要走原生反编译的任务：先如实报告“当前缺引擎”，给出两个选项（装 Ghidra 后配 `GHIDRA_INSTALL_DIR`，或用黑盒路线：字符串、资源、包清单、运行时观察）。**不要假装分析过，也不要因为缺引擎就宣布整条路线不可用。**
- 纯黑盒也常常够用：包清单 + 字符串 + 资源 + 网络行为，能回答“它大概怎么工作”，只是回答不了“具体哪一行”。
- **Go 程序的黑盒收益特别高**（实测 `dnsx.exe`，29 MB）：字节里有 `go1.25.0` 版本串和成串的 `github.com/xxx/yyy` 模块路径，直接读出依赖树。实测命中 `miekg/dns`、`utls`、`goleveldb` —— **从依赖就能推断它是 DNS 工具、且带 TLS 指纹伪装能力**，全程不需要引擎。
- **不要手写 PE 结构解析**。实测手工读 `OptionalHeader.Subsystem` 时偏移算错（把 Characteristics 当成了 Subsystem，读出 34 这种不存在的值）。要结构信息就调 REA 的 `inspect_pe_resources` / `inspect_binary_layout`，比自己 `struct.unpack` 可靠。

## 常见失败模式

| 失败 | 症状 | 正确做法 |
|---|---|---|
| 把反编译输出当书来摘要 | 产出一堆函数说明，没人能用 | 先有问题清单，只为解决问题取证 |
| 文件名推断行为 | “这个叫 updater 的模块负责更新” | 找到实际调用点再说 |
| 静态当动态 | “程序会请求 X” | 说“存在请求 X 的代码路径”，除非有运行证据 |
| 对比不可比 | “两版没有差异” | 核对页集完整、provider 一致 |
| 重复分析 | 同一个二进制反复 open、反复 overview | 先查 `binary_session`，复用既有会话 |
| 过早全量反编译 | 上下文被淹没，关键结论被埋 | summary 优先，定点钻取 |
| 把打包当源码 | 在 ASAR 里找“源码目录” | 已打包产物只有打包后的形态，源码缺失就是缺失 |

## 取证之后：要变成自己的东西 → 读 `TAKE.md`

本文件管「把程序变成可追溯的知识」，**终点是一份理解报告**。
如果目标不止于理解，而是要**拿到源码 / 提取功能机制 / 做出自己的版本**，接着读 `TAKE.md`：
四层融合模型（功能/协议/架构/原理）、ORRI 四步、按平台拆（原生 / Flutter / RN / Electron / Unity）、
重建次序（协议 → 转换 → 业务）、以及本机工具链的实测缺口。

**一句话分工**：本文件回答「它是什么」，`TAKE.md` 回答「怎么变成我的」。

## 与文本消化的合并

程序消化的成果与文本消化的知识项进同一个库，靠统一收据结构对齐。合并时的额外规则：

- 程序证据的坐标只在**对应 SHA-256 的产物**内有效，产物换版本，坐标全部作废，需要重新取证。
- 推断档的主张进长期知识库时要降级标注，不能在同一次合并里被提升为观察。
- 与文本来源冲突时，以可复现的证据优先；两边都不可复现，就并列保留，不投票。
