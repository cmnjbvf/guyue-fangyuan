# 同类项目图谱（2026-10 实查）

炼化不是独门生意。市面上已有工业级同类系统，分两类：**把东西变成技能**，和**把东西变成记忆**。

## A 类：把任意材料变成可复用技能（最贴近本技能）

### Hermes Agent `/learn` — Nous Research，MIT

- 命令：丢一个目录（代码、API 文档、PDF、配置），产出结构化 `SKILL.md`
- **三层渐进披露**：Level 0 全库索引（约 3k tokens）→ Level 1 单个 SKILL.md → Level 2 技能内的 references
- 产物结构固定：`When to Use` / `Procedure` / **`Pitfalls`** / **`Verification`**
- 后台 **Curator**：空闲 2 小时后自动运行，把技能按 `active → stale → archived` 走生命周期，合并近重复
- 遵循 agentskills.io 开放标准，与 Claude Code、Codex CLI 互通

**它验证了什么**：本技能的"总地图 + 按区手册按需读取"就是这个三层结构的本地手写版。不是拍脑袋，是行业标准做法。

### SkillBank — MIT

- 每完成一个任务，**第二次 LLM 调用**把解法蒸馏成强类型技能对象（name / description / code / tags），存向量库
- 新任务先检索 top-k 相似技能做少样本注入
- **近重复判定：余弦相似度 ≥ 0.92 直接跳过**
- 每个技能记录 `use_count` 与 `success_rate`

**它验证了什么**：去重必须有阈值。靠人判断"这两个一样吗"永远判不完。

### SkillClaw — 高德 AMAP-ML，MIT，arXiv 2604.08377

- 本地代理拦截 Agent 请求并记录会话；evolve server 后台跑进化
- 核心是 **Agentic Evolver**：自主决策 **Refine（改旧的）/ Create（建新的）/ Skip（不动）**
- 验证队列保证技能"只升不降"
- 跨会话、跨 Agent、跨设备累积

**它验证了什么**：新经验进来时，第一反应不该是"写一条新的"，而是先问"该改、该建、还是该跳过"。

## B 类：把任意材料变成记忆图谱

### Cognee — Apache-2.0，约 2–3 万星

- **ECL 流水线**：Extract（38+ 格式摄入）→ Cognify（LLM 抽实体与关系）→ Load（图 + 向量 + 关系三库同写）
- **memify**：摄入后剪掉过时节点、给高频边加权、补充派生事实
- **页面级 provenance**：每条知识能追回原文档的哪一页
- 14 种检索模式，MCP server

**它验证了什么**：来源可追溯（provenance）不是可选项，是知识库能不能用的分界线。这直接对应本技能的「锚定率 ≥90%」。

## 2026-10-27 补充：合并/收敛这条线上还有谁

**这一节只记「谁讲过合并」，具体怎么做在 `MERGE.md`。** 不重复内容。

### skill-organizer（massgen/MassGen，1,142 stars）

- 读所有已装技能 → 找重叠 → 合并成层级父技能 → 生成 `SKILL_REGISTRY.md` 路由指南
- **给出容量数字**：技能选择容量 κ ≈ 50–100 项，超过后准确率下降
- **三条硬约束值得抄**：① 不许用关键词匹配 / Jaccard 相似度 / 启发式分类，要读懂"它做什么"；② 要敢合，少而精胜过多个重叠；③ 合并时保留全部附带资源（模板/示例/配置）
- 它验证了什么：**去重不能靠算相似度，得靠理解**。这解释了 SkillBank 的 0.92 阈值为什么只够做"完全重复"的初筛

### Anthropic 官方《Building agents: When to fold subagents into your main agent loop》

- 讲的是**什么时候把 subagent 折叠进主循环**，是目前最权威的合并方法论
- 三条合并判据：**互相接续产出 / 碰同一批数据 / 经常被一起调用**
- **给了容量线**：系统提示超过 **30–50 个工具定义**后 tool choice 退化
- **给了反例**：折叠一个 subagent 后延迟降了，但一个原本通过的流程坏了（主 agent 自己答了，没问专家要交付日期），而且这个 break 只在两次运行中的一次出现
- 它验证了什么：**合并是变更，不是整理文件**。必须建 eval、逐任务比对、跑不止一次

### GSE（Globalized Skill Evolution）

- 技能库超 30 条且描述被截断 = 合并信号
- 按"rationale 语义相似"聚类，不是按表面关键词
- **Replay Verification**：合并后用历史任务回放，退化就 rollback
- 附带一个观察：技能质量对**弱模型**的杠杆更大（mini-SWE-agent 从合并中受益比 OpenHands 多）

### EvoSC（arXiv 2026，自进化 agent 的自我固化）

- **失败比成功信息量大**：同类任务的成功长得都一样，失败才会在关键决策点分岔
- 做法是把失败轨迹和成功轨迹**配对**做对比反思，问"逻辑在哪一步分叉"
- 双记忆：短期文本队列（FIFO）+ 长期参数化压缩
- 它验证了什么：**炼化时只收成功案例，会漏掉最值钱的部分**——为什么另一种做法会坏

### 87→70 收敛实证（ai.rundatarun.io 一篇个人实践）

- 三个月从 33 个技能涨到 87 个（+163%），然后收敛到 70 个
- 三种合并模式：Mode-Based / Feature-Based / Audience-Based（详见 `MERGE.md`）
- **Archive Don't Delete**：24 个技能归档进 `_archived/`，不删
- 语言层面：攻击性大写（CRITICAL/MUST/NEVER）和 `think` 一词可能降低稳定性
  ⚠️ **这条标"待验证"**——本项目未复现，而且与本技能通篇用 ⛔/🔴 的风格冲突

## 与本技能的差异

| 维度 | 它们 | 本技能 |
|---|---|---|
| 形态 | 常驻服务 / 后台 daemon / 向量库 | 单目录的 Markdown 文件，随读随用 |
| 依赖 | Python 服务、图数据库、嵌入模型、API key | 无（除已装的 MarkItDown / Repomix） |
| 增量知识 | 写入数据库，检索注入 | 写入 references，靠地图按需读 |
| 数据出不出本机 | 视部署，云版要上云 | 全程本地 |
| 适用规模 | 成百上千个技能、多人共享 | 单人单机、几十个技能 |

**结论：不直接装。** 它们是"多人、长期、大规模"的解法，本机是"单人、本地、够用就好"。装一套图数据库来管 18 个 Markdown，是负收益。

## 吸收了什么（并进本技能的机制）

| 机制 | 来源 | 落在哪 |
|---|---|---|
| 来源可追溯 / provenance | Cognee | SKILL.md 铁律 3「每条结论都要有落点」+ QUANTIFY 锚定率 |
| 渐进披露三层 | Hermes | 总地图 65 行 + 五区手册按需读 |
| **Verification 一节** | Hermes | 见下方「交付自检」 |
| 去重阈值思想 | SkillBank | PLAYBOOK 的"同一材料第二次读不出新东西就停" |
| Refine / Create / Skip | SkillClaw | 新增内容前先问：改旧的、建新的、还是不动 |

## 没吸收的（以及为什么）

| 机制 | 为什么不 |
|---|---|
| 后台 Curator 自动维护 | 需要常驻进程。本机是"用到才醒"，没有常驻。改为**手动触发**：用户说"整理技能"时才跑 |
| 向量库 + 嵌入检索 | 只需管 18 个文件，目录名和 description 就够了，上向量库是杀鸡用牛刀 |
| 多人共享 / 跨设备同步 | 单人单机，没有这个需求 |
| 自动 Refine 改写技能 | 技能是用户的资产，自动改写风险太高。改为"发现问题就报告，等确认再改" |
