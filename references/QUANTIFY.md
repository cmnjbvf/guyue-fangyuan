# 量化：多少料，花多大力气

炼化的头号浪费不是炼错，是**用炼一本百科全书的力气去炼一页纸**，或者反过来。

## 一、先算料，别猜

不看文件大小，看**可判断单元有多少**：

| 区 | 单元 | 怎么数 |
|---|---|---|
| 文本 | 段 | 段落数，不是字数 |
| 文档 | 页 | 页数；跨页表格整体算一个 |
| 代码 | 函数 / 类 | 排除依赖、产物、样板后的数量 |
| 软件 | 功能点 | 不是函数数（函数太多且多为库代码） |
| 对话 | 话题片段 | 不是消息数（一条消息常常半句话） |

**不同区的单元不能互相换算。** 拿"1 万行代码"和"1 万字聊天"比大小，没有意义。

## 二、五档投入

| 档 | 规模（折算后） | 做法 | 产出形态 |
|---|---|---|---|
| **T0** | ≤2k 字 / 1 个文件 | 一次读完直接炼，不上工具 | 对话里直接给 |
| **T1** | ≤2 万字 / ≤5 文件 | 通读，边读边记，一遍出稿 | 单个 Markdown |
| **T2** | 2 万–10 万字 / 5–50 文件 | 按结构切块，每块出卡，最后合并 | 卡片集 + 合并稿 |
| **T3** | 10 万–100 万字 / 50–500 文件 | 分批 + 并行子代理，主代理收口 | 索引 + 分区产物 |
| **T4** | >100 万字 / >500 文件 / 整个仓库 | **默认先出骨架**；用户明确要全量时 → 分批全量做，批间对账 | 默认：结构图 + 按需深挖；全量：分批产物 + 累计账本 |

**规模只改变分批与调度，不改变目标。** T4 默认先出骨架，是因为没人提前说过要全量；**用户明确要"全部消化"时，就用"分批处理、保存结果、持续对账"的方式做全量**——大资料不需要一次装进上下文，但也不许因为大而自动降级成摸底。

**在 T4 追求全覆盖不是伪目标，只是不能靠一口气硬读**——分批、存结果、对账，做到哪算到哪，账目清楚。

## 三、密度修正

同样 2 万字，实际信息量能差五倍。定档前先折算：

| 原料 | 密度系数 |
|---|---|
| 代码 | ×3（按行数折算） |
| 技术文档 / 规范 | ×1.5 |
| 学术论文 | ×1.2（公式与表格另计） |
| 口水聊天 | ×0.3 |
| 同一意思反复说 | 先判重，再按去重后计 |

**判档用折算值，不用原始字数。** 十万字口水聊天可能只是 T1，五千行代码可能已经是 T2。

## 三之二、各区的尺子怎么换算

上表的档位是按"折算后字数"划的，但文档和对话不按字算。换算口径：

| 区 | 主尺 | 换算成字 |
|---|---|---|
| 文本 | 折算后字数 | 直接用 |
| **文档** | 页数 | 1 页 ≈ 1200 字（密排 1500，图多 800） |
| **代码** | 行数 ×3 | 文件数只当副尺，不当主尺 |
| **软件** | 功能点 | 不换算，按功能点直接定档 |
| **对话** | 话题片段 | 约每 20–30 条消息算 1 段；**取料后才能定**，取料前只能说"待定" |

举例（括号里标的是定档时点）：

- 320 页扫描件 ≈ 38 万字 → **T3**（取料前就能定：页数本身就是单元数）
- 3 万行 TS ≈ 9 万字，但 300 个文件 → **T3**（两把尺取高）
- 8000 条私聊 → **取料前标"待定"**。抽样 200 条判出约 25 条/段，则 8000÷25 ≈ 320 段；每段 50–150 字，折 1.6–4.8 万字 → **T2**

**只有对话区允许"待定"。** 文本、文档、代码、软件的单元数在取料前就能估准，不许拿"待定"当拖延借口。

**取料前定不了档是正常的。** 先做取料这一步，拿到真实单元数再定档，不许拿文件名和体积硬猜。

## 三之三、两把尺打架怎么裁

同一个东西，不同尺给出不同档：3 万行代码 ×3 = 9 万字（T2），但文件数 300 个（>50，按 T3）。

**裁决：取更高档，不取平均。**

理由：低估档位的代价是做到一半发现做不完，返工成本远大于一开始多花力气。宁可高档慢做，不要低档做崩。

唯一例外：高档做法会破坏质量时降一档并说明。典型情况是 T3 要求并行、但这批材料彼此强耦合切不开——那就降为 T2 串行，写明"因耦合切不开而降档"。

## 四、五个可核对指标

每轮炼完自己算，不许凭感觉说"炼好了"：

| 指标 | 算法 | 及格线 |
|---|---|---|
| **覆盖率** | 已处理单元 ÷ 总单元 | T1–T2 ≥95%；T3 ≥80%；T4 按约定范围 100% |
| **锚定率** | 有落点的主张 ÷ 全部主张 | ≥90%。低于 90% = 感觉流 |
| **提取率** | 主张数 ÷ 单元数 | 0.5–3 条/单元。高于 3 说明在拆废话 |
| **冲突率** | 互相矛盾的主张 ÷ 全部主张 | >10% 必须单列，不许合并抹平 |
| **可用率** | 下一步真用得上的 ÷ 全部产出 | ≥60%。低于 60% 说明在自娱自乐 |

**锚定率是最硬的指标。** 它掉下来，其余四个都没意义——没法回查的结论，写得再漂亮也是猜的。

## 四之二、覆盖率必须分层算，一个总数会骗人

实测一单：11 个源目录、125,889 文件、50.7 GB，最后精读 446 篇 / 13.8 MB。**按总量算 0.03%，看起来像什么都没干。**

分层看才清楚：

| 层 | 里面是什么 | 该不该读 |
|---|---|---|
| **分析层** | 人写的结论、报告、审阅、方案 | **必须读**，知识在这一层 |
| **语料层** | 采集的原文、转录、下载的资料 | 按问题取样，不全读 |
| **生成层** | 索引、队列、机器批量组合的中间产物 | 基本不读——读它等于读自己 |
| **素材层** | 源码、二进制、图片、音视频 | 走代码区/软件区，不计入文本覆盖 |

那一单分析层覆盖 16.3%，但**结论层与工程层接近全覆盖**，所以它是成功的；语料层 830 MB 全未读，是**刻意不读**，并在账本里写明了原因。

**报覆盖率必须带层名。** 同一个"3%"，可能是"该读的都读了"，也可能是"根本没动"——不带层名的覆盖率和没报一样。

**术语纪律**：投入档位叫 T0–T4，数据分层叫分析层/语料层/生成层/素材层。**两套东西不要共用同一个编号**，否则“T1 覆盖率 95%”到底是哪层没人说得清。

## 四之三、有些东西不读完，不算完成

**“诚实报覆盖”不等于“可以少读”。** 两件事混在一起，就会出现最难查的失败：**账报得很老实，活只干了一半，还理直气壮——因为它确实没撒谎。**

三条硬线，不满足就不许说完成：

1. **分析层必须 100%。** 人写的结论、报告、审阅、方案——知识就在这一层。实测一单：分析层去重后 2,498 篇，只读了 446 篇（17.9%），账写得清清楚楚，但**84% 的知识没进来**。诚实救不了这个缺口。
2. **二手转述不算读过。** 拿别人的总结当原文，比没读更危险——会让人以为读过了。必须找原始材料；实在找不到，写“仅二手，未经原文验证”，并计入未读。
3. **素材层里的源码不算文本覆盖。** 源码走代码区、按 T4 出骨架；不要用“代码没读”去冲抵分析层的缺口，两码事。

**覆盖率可以低，但必须低在这三类之外。**

配套的自检问题：**这次没读的部分，如果用户明天追问，我能不能立刻指出去哪一篇读？** 指不出来，就不是“取舍”，是“没干”。

## 五、什么时候停

| 停法 | 判据 |
|---|---|
| **饱了** | 新增材料的边际产出 < 已有产出的 5% |
| **够了** | 用户的问题已经能答全 |
| **卡了** | 同一处卡三次 |

卡了必须停下报缺口，不许硬磨。磨出来的东西既不可靠又费时间。

**反完整主义**：把 100 万字全过一遍，不如把回答用户问题的那 5 万字炼透。完整性不是炼化的目标，"能用"才是。

## 六、激进取舍的三条

这三条不保守，但对：

1. **看不懂的段落直接标"未覆盖"跳过**，不猜。猜出来的内容会在下游变成假前提，代价远大于留白。
2. **同一材料第二次读不出新东西就停**。重复阅读是最常见的假勤奋。
3. **能一句话说清的不写三段**。产物是给人用的，不是给人看的。

## 七、产出物本身要过关

炼完的产物，拿出来自检：

- 能不能不看原料就把这份产物用掉？不能 → 说明还依赖原料，没炼完
- 每一条主张，能不能在 10 秒内指回原料的某处？不能 → 删掉或降级为推断
- 有没有一句话是"正确的废话"（比如"该模块负责处理业务逻辑"）？有 → 删掉

最后一条最省事也最有效：**把产物里随便挑三句，看有几句能被证伪。** 一句都不能证伪的，那份产物大概率没用。

## 八、提速：哪些真有用，哪些是幻觉

按实测收益排序。**加速的前提是先知道时间花在哪**——那一单 7.7 小时里，3 小时干活、4.4 小时返工。

| 手段 | 收益 | 代价 | 判定 |
|---|---|---|---|
| **消除返工** | 历史观察：返工曾占总时长 **57%**。定规范可消除此类返工，节省幅度待实测 | 开工前 30 秒定规范 | ✅ 首选 |
| **三级阅读** | 省 40–60% 的全文读取 | 多做一轮判断 | ✅ 次选 |
| **并行派 agent** | 理论 N 倍，实际 **3–5 倍** | 协调开销 + 主代理上下文 | ✅ 量大才用 |
| **分级模型** | 成本省一半以上 | 初筛质量略降 | ✅ 只用于初筛 |
| **脚本替模型** | 快百倍 | 只能干机械活 | ✅ 必做 |
| 压缩卡片字数 | 省一点时间 | **质量下降且不可逆** | ❌ 不值 |
| 读摘要代替原文 | 省很多 | **等于没读** | ❌ 红线 |
| 并发堆到 20+ | 边际递减 | 上下文必爆 | ⚠️ 适可而止 |

### 三级阅读（最被低估的一条）

不要每篇都精读。分三级，每级只问一个问题：

| 级 | 看多少 | 判什么 | 不过关怎么办 |
|---|---|---|---|
| **1 扫读** | 约 200 字：标题 + 首段 + 小标题 | 这个主题，已有卡片覆盖了吗？ | 疑似覆盖 → 标 `疑似重复`，**进比较队列**（哈希或抽正文核对），不许直接跳过 |
| **2 读** | 全文 | 有没有可执行结论 / 数字 / 反例？ | 没有 → 标 `无增量`，跳过 |
| **3 精读** | 全文 + 回读上下文 | 出卡 | — |

**实测对照**：那一单分析层 2,498 篇（去重后），**精读 446 篇**、产出 486 张卡。若先扫读筛掉疑似重复与无增量，精读预算能集中在更有价值的篇目上——**此为预期收益，待实测验证**。

注意：`疑似重复` 和 `无增量` 都要**留记录**（标题 + 判定 + 一句理由），不能静默跳过。

**重复分三档，只有一档能直接跳**：全文哈希一致 = 精确重复（可复用跳过）；扫读发现主题相似 = 疑似重复（**进比较队列**，核对正文增量后才能定）；核对正文后确认无独立增量 = 才能标 `无增量`。**扫读只能产生"疑似"，永远产生不了"确认"**——标题普通的文档，正文里可能藏着新条件、新反例、新版本。

### 提速的天花板

单篇精读的成本降不下来——模型读一篇、想清楚、写出一张有用的卡，物理上就是几十秒到几分钟。

所以提速只有两条路：**少读**（三级筛选）或 **同时读**（并行）。

**想靠"读快点"提速，是幻觉。** 说得出这句话，才不会被各种"优化"忽悠。
