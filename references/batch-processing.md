# 大批资料：覆盖、收据与恢复

当资料需要分轮读取、混合提取、续跑或用户明确要求完整覆盖时读取。短材料可以直接完成，不为小任务创建一套账本。

## 两条路线（先选这条，再往下看）

处理大批资料有两条路，**产物不同，别混**：

| | **A 严格对账型**（本文件主路） | **B 并行跑批型** |
|---|---|---|
| 适合 | 结论要能逐条回查原文、要续跑、要报覆盖率 | 只要通读全部、产出一份大笔记 |
| 工具 | `scripts/digest_batch.py`（清点/分段/哈希/收据对账） | `scripts/chunk.py` + `scripts/merge_corpus.py` |
| 做法 | 逐段精读 → 写收据 → `audit` 对账 | 分块 → 并行派子代理 → 融合 |
| 产物 | 知识卡 + 收据账本 | 批次笔记 ×N + 一份大笔记 |
| 强项 | 可核验、可续跑、覆盖可报 | 快、不停机、不漏段 |
| 弱在哪 | 慢（每段都要写收据） | 不可对账（只有叙事，没有证据链） |

**判据一句话**：这批材料的结论**将来会不会被人质疑**？

```
会被质疑（要给别人看、要引用、要下判断） → A
只是自己通读一遍                            → B
```

**混合用法**：B 跑完全部批次拿到大笔记，再对其中**最关键的那几批**补 A 的收据——既不慢，关键处又立得住。

### 路线 B 的四条铁律（从并行跑批实践吸收的）

1. **原文永不进主对话。** 大文本第一步整体落盘，此后一切读取走文件。
   **禁止把 chunk 内容贴回主对话"自己读"**——那等于没分批。
2. **每批字段统一。** 所有批次用同一个模板（`templates/extraction-template.md`）。
   字段对齐是融合质量的第一杠杆。
3. **中途不停机。** 跑完一批记一笔，直接派下一批（例外见下）。
4. **每条结论标来源批次。** 大笔记里每个结论标 `[批次N]`；没有溯源的不进核心结论区。

### 停机规则（只有这三种情况才准停下来问）

1. **不可逆操作**（删用户文件、覆盖已有产物）
2. **任务范围变化**（中途追加了完全不同的需求）
3. **规模数量级爆炸**（比如原文 500 万字、要跑 1000 批——报成本、给选项）

**其余情况一律跑完再说话。**

### 什么时候**不**该分批

| 情况 | 用什么 |
|---|---|
| 文本 < 3 万字符 | **直接读**，别切 |
| 针点查询（找某个词/某段） | **`Grep`**，别整本切 |
| 只需检索、不需通读 | **RAG 式按需检索**，别整本切 |
| 只要有结论、不要证据 | 先问清用途，可能要的其实是路线 B |

### 五个反模式（都会直接毁掉产出）

| 反模式 | 为什么毁 |
|---|---|
| 把 chunk 贴回主对话"自己读" | 上下文撑爆，注意力稀释原样发生，分批失去意义 |
| 固定等份切 | 一个观点从中间斩断，每批只看到半句话 |
| 批次笔记自由发挥 | N 份笔记字段对不上，融合变浆糊 |
| 跳过交叉核查 | 跨批次矛盾全漏，大笔记看着干净实则残缺 |
| 失败一批就全线中断 | 应**单批重试一次 + 记录跳过** |

### 路线 B 的产物模板（三件，都在 `templates/`）

| 模板 | 给谁用 |
|---|---|
| `extraction-template.md` | 每个子代理做批次笔记时照它填 |
| `subagent-prompt.md` | 派活时把这段贴给子代理（它看不到主对话） |
| `master-note-template.md` | 融合大笔记的结构 |

**断点续跑（B 路线）**：开始前先查 `<run-dir>/PIPELINE_STATE.md`，存在则从记录的阶段续跑，已产出的 chunk 和批次笔记不重做。

### 抓取与分批的分工（零网络 vs 管网络）

**分批本身不管抓取。** 大规模爬取是两个环节接力：

```
① 抓取：用专门的抓取工具（robots 合规、懒加载、断点续传、按栏目归档）
   —— 合规与频率归它管，不归本文件
② 合并：scripts/merge_corpus.py 把抓取产物目录打成单一 source
③ 分批：按上面选的路线（A 或 B）正常跑
```

**规模提示**：N 上百批时，Map 按主题/栏目**分多轮派发**（每轮 5–8 个），Reduce 二级合并照常；N 上千或原文百万字级，先按「停机规则」第 3 条报成本再跑。

## 分工和范围

`scripts/digest_batch.py` 仅做确定性清点、字符分段、哈希、引文跨度与收据对账。它不执行来源命令、不调用模型或联网、不直接导入领域知识库、不证明语义正确。原文格式解析和知识提取仍由当前 Agent 按任务完成。

脚本只使用 Python 标准库。用当前已核对的 Python 执行；不要为了调用它安装依赖或修改全局 PATH。输出放用户选定根下 `.digest-runs/<批次ID>/`，正文成果沿用用户指定结构。已有运行不覆盖；原件内容变化须建立新批次，旧记录继续保留。

## 输入与准备

`prepare --source <绝对文件或目录> [可重复] --output-root <目标绝对路径> --batch-id <安全ID> --goal <用途> --domain <领域> [--profile generic|domain-profile] [--chunk-chars 12000] [--recursive] [--extractions <绝对JSON文件>]`

目录默认只处理该层，递归必须明确选择；跳过 Git、链接和输出子目录。仅授权来源进入清单，不扫其他资料。输出路径含链接时脚本拒绝；Agent 可先核对真实目标并使用已确认的物理路径，不能借此改变用户目的地。

TXT/MD/Markdown/JSON/JSONL/CSV/TSV/log/YAML/XML/HTML 等以 UTF-8 原样文本保存；这不是 JSON/表格/HTML 语义解析。非 UTF-8 或其他格式登记需提取。空文件单列，不当作已取得知识。正文保留实际字符，不静默删除空白或 BOM。

二进制、文档、图片和音视频先用当前已授权工具取得正文，映射文件形如：

```json
[{"source":"D:/资料/原件.pdf","text_file":"D:/提取结果/正文.txt","method":"实际使用的工具和配置"}]
```

记录原件与提取文本哈希；不能拿伪造的页码代替规范化字符位置。需要页码、元素或时间定位时另保存工具实际返回的对应表，并核验原件→提取结果完整性。未取得正文始终列为 needs_extraction。

## 逐段精读与记录

1. prepare 返回 run、来源与片段数，查看 manifest 和 chunks。分段预算可调，12000 字符只是传输默认值，不是知识卡篇幅、token 承诺或批次上限。脚本尽量按换行切分；Agent 仍须按章节、记录、表格和语义依赖调整读取范围，不将边界当成知识独立性证明。
2. `read --run <绝对运行目录> --chunk-id <ID>` 取得完整片段及分开的邻接上下文。必要时回读父节、其他片段、表头或脚注；邻接上下文不是本片段新增覆盖。
3. 由模型提取知识项，写收据 JSON，`record --run <目录> --receipt <绝对JSON路径>`。引用使用保存正文的绝对字符偏移 `[start,end)` 与逐字 quote，不是字节或原 PDF 页码。

```json
{
  "chunk_id":"prepare返回的ID",
  "disposition":"extracted",
  "reason":"提取适用条件和操作步骤",
  "claims":[{
    "id":"稳定知识项ID",
    "statement":"有来源支持的知识表述",
    "kind":"experience",
    "evidence":[{"start":0,"end":6,"quote":"此处仅示意"}],
    "conditions":[],"exceptions":[],"uncertainties":[]
  }]
}
```

示例偏移只是结构说明，实际必须与原文匹配。一条主张跨多个片段时，各片段记录其局部证据，综合产物关联多个知识项；不把相邻上下文的字面内容伪装成本块证据。

收据终态为 `extracted / duplicate_no_increment / no_reusable_knowledge / needs_review`，均需理由。extracted 必须有带证据的知识项；未读内容不能标无价值。重复须明确 `duplicate_of`：已存在片段收据使用 `{type:chunk_receipt,chunk_id:...}`；已有知识使用 `{type:existing_knowledge,id:...,locator:...}`，语义等价仍由模型核对。

相同收据重复提交幂等，不同内容默认拒绝。复核后修正使用 `record ... --replace-receipt-sha <当前收据SHA256>`，旧收据追加保留在 receipt-history；hash 不符停止，不能覆盖后来修改。

## 中断和最终对账

`audit --run <目录>` 为只读：列出来源、片段、已处理/未处理、待复核、需提取、读取错误、空文件与字符覆盖。退出码 0 表示机械完成，2 表示 partial，1 表示输入/哈希/结构错误。每次 read/record/audit 都核对来源、保存正文和分段哈希；漂移不静默续用。

中断后审计原运行，按未处理清单继续。复核完的 needs_review 收据显式修订；原件或提取方法变化建立新批次，不能把旧收据算作已验证新材料。只复用哈希与处理配置相符的结果，近似重复仍人工判断。

机械完成只说明文本片段都有去向和引文字面一致；语义质量恒为 `not_machine_verified`。最后仍做原文→产物查遗漏、产物→原文查扩写，并用用户实际问题试用。没有原件解析完整性证据时，覆盖率的分母只能是已取得的正文，不能扩称全部原件。

## 收据合同的适用范围（先读这条再写收据）

`digest_batch.py` 的校验器**只认一套词表和一种定位**：

- kind 白名单：`fact / experience / inference / preference / unknown`（写 `observed`、`inferred` 会被拒）
- evidence 定位：已保存正文的**字符区间** `[start,end)` + 逐字 quote（页码、行号、程序地址、消息 ID 都会被拒）

所以收据分两种，**别混**：

| | 文本区批量任务 | 其他区（软件 / 代码 / 文档 / 对话） |
|---|---|---|
| 收据性质 | **真收据**，进脚本校验 | **概念模板**，形状对齐但**不走脚本校验** |
| kind 词表 | 必须用上面五类 | 语义三档映射：观察→`fact`/`experience`、推断→`inference`、未知→`unknown` |
| evidence | 字符区间 + 逐字 quote | 各区自己的坐标（页码 / 行号 / 地址 / 消息 ID） |
| 校验方式 | `digest_batch.py` 自动 | 各区自检 + 人工抽查 |

**待办**：将来扩展脚本校验器，统一接受多区坐标——在那之前，其他区的收据别喂给脚本。

## 批量交付的三件门面（缺一件就等于没交付）

批量跑完，光有卡片不算交付。**没有门面，几百张卡就是一堆孤岛。**

| 门面 | 回答什么 | 缺了会怎样 |
|---|---|---|
| **总索引** | 从哪开始读、按问题怎么找 | 卡再多也没人翻 |
| **覆盖账本** | 读了什么、没读什么、为什么 | 用户不知道拿到的是全貌还是碎片 |
| **来源地图** | 每个源是什么、产出哪些卡、还剩什么 | 无法判断某个结论能不能信 |

三件**各自单独成文件**，不要塞进卡片、也不要只在对话里说。

### 总索引最低要求

- 一页看完（目标 ≤10 KB）
- **先读这几张**：按重要性排，每张写“为什么先读它”
- **按问题找卡**：把用户可能问的问题列成表，指到卡 ID
- 引卡只写 `ID + 短标题`，不写文件名

### 覆盖账本最低要求

- 分层报覆盖率（分析层 / 语料层 / 生成层 / 素材层），见 `QUANTIFY.md` 四之二
- 未读清单**具体到目录与体量**，不许写“部分未读”
- 一句总结：哪些读到了、哪些是刻意不读、为什么

### 来源地图最低要求

- 每个源一行：它是什么 / 体量 / 产出哪些卡 / 未读部分
- **标出“只经二手转述”的源**——这类结论不能当一手，引用时必须标明

## 产出目录与增量

- **按族分目录**：一个族一个目录（如 `02-机制卡/`、`03-架构卡/`），不要 486 个文件全堆在根下
- **增量消化**：已有卡片库时，写之前先搜已有索引，只写增量；卡里注明“补充 X-0xx”
- 增量卡单独标出，让用户一眼看出哪些是新结论、哪些是继承的

## 单卡规格

- 一张卡只说一件事，600–1600 字；超了拆卡
- frontmatter 必须有**可执行度**（高/中/低）：能不能直接照着改代码。没有这一项，读者无法快速判断哪张卡能动手
- 标题 ≤30 字，具体，不写“概述”“分析”这类空词
