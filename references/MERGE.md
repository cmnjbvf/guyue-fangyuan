# 合并与去重：把 N 个东西变成 1 个

**这份文件解决什么**：手上有一堆功能重叠的技能 / 文档 / 配置，想合成一个更强的。和 `PLAYBOOK.md` 里"批处理时合并子代理产物"是两件事——那个讲流程，这个讲**结构合并**。

**先分清三种"合并"，混在一起必出事**：

| 类型 | 场景 | 判据 | 去哪 |
|---|---|---|---|
| **产物合并** | 8 个子代理各交一份报告 | 同一件事出现 8 个版本 | `PLAYBOOK.md`「主代理收口」 |
| **结构合并** | 5 个技能都在管"代码质量" | 触发词抢同一句话 | **本文件** |
| **内容归并** | 同一段知识写在 3 个文件里 | 改了 A 忘了改 B | 本文件 + `PLAYBOOK.md` 脚本去重 |

---

## 一、什么时候该合并（三个硬信号，够一个就动）

### 信号 1：越过容量线

> 【多源印证】模型对技能/工具的选择准确率会随数量下降：
> - `skill-organizer`（massgen/MassGen, 1,142 stars）称技能选择容量 **κ ≈ 50–100 项**，超过后选择准确率下降
> - Anthropic 官方《When to fold subagents into your main agent loop》：**系统提示里超过 30–50 个工具定义后，tool choice 会退化**
> - GSE（codex.danielvaughan.com）给的运维信号更早：**超过 30 条且描述开始被截断，就该合并了**

**落到执行**：技能数到 50 就开始按本文件走一遍；到 100 之前必须收敛过至少一次。

### 信号 2：触发词抢同一句话

不是"描述看起来像"，是**同一句用户话能同时命中它俩**。
判法：把每个技能的 description 摊开，找出"用一句话就能让两个都想接"的对子。找得到就是重叠。

### 信号 3：一次任务里连着调用两个以上

Anthropic 官方给的三条合并判据，原文：

> *"Merge specialists that chain on each other's output, touch the same data, or are often called together."*
>（合并那些**互相接续产出**、**碰同一批数据**、**经常被一起调用**的专家）

**"经常被一起调用"是可测的**：翻历史会话，看 A 出现后 B 跟上的比例。Anthropic 的说法是"如果相当比例的流量是 A 之后跟 B，这就是一对紧耦合"。

## 二、按什么合（三种模式，选错会合成四不像）

来源：一篇把 87 个 Claude Code 技能收敛到 70 个的实证文章（ai.rundatarun.io），三种模式都跑通过。

### 模式 A · 按"模式"合（Mode-Based）

**特征**：做同一件事，只是参数不同。
**做法**：合成一个带 `modes` 的父技能。

```
合并前：meeting-notes-processor / extracting-meeting-insights / action-items-tracker
合并后：meeting-processor，modes: summary(默认) / insights / action-items
```

**判据**：三个技能的差别能不能写成一张参数表？能 → 用这个模式。

### 模式 B · 按"功能"合（Feature-Based）

**特征**：是一个大能力的子功能，用户根本不关心底层区分。
**做法**：合成一个，内部列 `capabilities`。

```
合并前：gemini(基础CLI) / generating-gemini-images(带预设) / creating-gemini-presentations
合并后：gemini-images，capabilities: 快速生成 / 预设生成 / 整套演示
```

**判据**：用户会不会说"我要那张图，不要那个预设版"？不会 → 用这个模式。

### 模式 C · 按"受众"合（Audience-Based）

**特征**：同一份输入，只是输出对象不同。
**做法**：参数化受众，一个技能出两种格式。

```
合并前：creating-manager-briefs / creating-team-updates
合并后：weekly-comms，modes: executive / team
```

**判据**：两个技能的输入完全一样吗？一样 → 用这个模式。

### 不该合的（原文明确保留的）

| 类型 | 为什么不合 |
|---|---|
| 文档处理器（docx / pdf / pptx / xlsx） | 各自体量已经很大，合了更难用 |
| 平台特定工具（slack / discord / imsg） | 不同 API、不同心智模型，合了没有收益 |
| 薄壳 CLI 包装器 | 补触发词就行，合了反而丢细节 |

## 三、选谁当主干（合并时的第一决策）

`skill-organizer` 给的判据，按优先级：

1. **指令质量更好**（写得更细、有具体参数、有反例）
2. **附带资源更完整**（scripts / references / 模板在哪个目录下）
3. **名字更通用**（`web-app-dev` 胜过 `react-frontend`）

**它还有一条硬约束，值得抄**：

> *"Do NOT use keyword matching, Jaccard similarity, or heuristic categorization. Use your understanding of what each skill does."*
> *"Be aggressive about merging: fewer high-quality skills beats many overlapping ones."*

**翻译过来**：别拿相似度算法算"这俩像不像"，要读懂它俩各自在解决什么问题；而且要**敢合**——一个写透了的父技能，胜过四个各写一点的子技能。

⚠️ 但"敢合"不等于"乱合"。下面第四节是刹车。

---

## 四、合完必须验（这是最容易跳过、代价最大的一步）

### 铁证：一次合并把通过的流程搞坏了

Anthropic 官方文章里写得很直白：

> 把 one subagent 折叠进主循环后，**延迟降了，但一个原本通过的流程坏了**——主 agent 自己拿着订单查询工具就答了，没去问运输专家要交付日期。
> 而且**这个 break 只在两次运行中的一次出现**。

→ 结论：**合并是有风险的变更，不是整理文件。**

### Replay Verification（GSE + Anthropic 都要求）

| 步骤 | 做什么 |
|---|---|
| ① 建基线 | 合并**前**，用原版技能跑一批历史任务，记下每个任务的通过/失败 |
| ② 跑合并版 | 用合并后的技能跑**同一批**任务 |
| ③ 逐任务比对 | **不要只看总分**——看**哪些任务翻转了**（原过今败才是信号，原败今过是意外收获） |
| ④ 每个任务跑不止一次 | 上面那个 break 只在 2 次里出现 1 次。单次结果不可信 |
| ⑤ 有翻转就回滚 | GSE 的原话：*"If a consolidated skill degrades performance on a task the original handled correctly, roll back."* |

**eval 覆盖面要求（Anthropic）**：生产环境里**一起跑的每条 agent 链**、**每条不能破的规则**，都要有对应用例。

### 没有历史任务怎么办

退化方案：把**原技能的 description 涉及的场景**各写一个最小用例，合并前后各跑一遍。至少覆盖"最常用的那条路"和"最危险的那条规则"。

⚠️ 连最小用例都写不出来的合并，属于"凭感觉整理文件"，风险自负。

## 五、归档，不删除

实证文章的原话是 **"Archive Don't Delete"**（它把 24 个技能归档进 `_archived/`）。

**理由很实际**：合并的判据不可能 100% 准。删了就回不来了，归档随时能捞。

**落到本机**：技能关了只是关开关，文件还在目录里——这就是天然归档。**别去删目录。**

## 六、三个容易忽略的细节

### 1. 按用户意图合，不按实现合

> *"Consolidate by User Intent, Not Implementation. Users don't think 'I need the meeting-notes-processor skill.' They think 'process this meeting.'"*

**判据**：新技能的 description 里，触发词是不是用户真会说的话？不是 → 合错了方向。

### 2. 失败比成功信息量大（EvoSC 的对比反思）

【学术，arXiv 2026】EvoSC 框架的一个发现值得抄进炼化流程：

> *"Successes within a task category often look identical, but failures diverge at critical decision points."*
> （同一类任务的成功长得都一样，**失败才会在关键决策点上分岔**）

**做法**：合并/提炼时，把**失败轨迹和成功轨迹配对**看，问"逻辑在哪一步分叉的"。只收成功案例的炼化，会漏掉最值钱的部分——**为什么另一种做法会坏**。

**这直接对应本技能的铁律 2**：炼化出来的"硬坑"清单，比"正确做法"清单更有价值。

### 3. 语言层面的坑（⚠️ 待验证，别盲信）

同一篇实证文章说：攻击性大写（`CRITICAL` / `MUST` / `NEVER` / `ALWAYS`）会让行为不稳定；`think` 一词会触发不必要的长推理（针对 Claude Opus 4.5），建议换 `consider` / `work through`。

**【待验证】**：本技能通篇用 ⛔ / 🔴 / "不许"这类强标记，与这条建议冲突。**我们自己的实测没做过 A/B，所以不采纳也不否定**——记在这里，等哪天真的因为这个出问题再回来看。

> 这正是铁律 4 的用法：观察、推断、未知三档分开。这条标成"未知"，不标"观察"。

## 八、执行顺序（照这个走，别跳）

```
【第一段：判】只读不动，产出结论

1. 数一遍现在有多少个 → 过了 50 吗？没过也可以因为重叠而合
2. 找重叠对子：同一句用户话能命中两个吗？（附证据：哪句话、命中哪两个）
3. 判模式：参数差异(A) / 子功能(B) / 受众差异(C)
4. 选主干：质量 > 资源 > 名字

🔴 STOP —— 把 1–4 的结论交出去，等用户点头

【第二段：做】用户确认后才进

5. 🔴 建基线：原版跑一遍历史任务，记下逐任务结果
6. 写新技能（把被合者的独有部分补进来，重复的只留一份）
7. 🔴 跑合并版同一批任务，逐任务比对
8. 有"原过今败"→ 回滚，并记录为什么
9. 关掉旧技能（不是删目录）
10. 在产物里写清：合了谁、留了谁、丢了什么、为什么
```

**第 5 和第 7 步是本文件的全部价值所在。** 跳过它们，这套东西就退化成"整理文件夹的仪式"。

**那个 STOP 是第三条价值所在。** 它对应 `PEERS.md` 里"技能是用户的资产，自动改写风险太高"——**判完就动手，等于替用户做决定**。

### STOP 时该交什么（一份，不是四份）

| 项 | 内容 |
|---|---|
| **冲突对子** | 哪几个之间、证据是哪句用户话、命中率多高 |
| **建议怎么合** | 用哪种模式（A/B/C）、谁当主干、理由 |
| **会丢什么** | 哪些独有内容可能保不住 |
| **代价** | 大概要跑几轮验证、动几个文件 |

⛔ **没交过这份东西，不许进第二段。** 用户说"你看着办"也算点头，但那份东西必须先出。

## 九、先用扫描器把冲突捞出来（能跑的那个）

MERGE 前三步靠读，读几十个技能会累且会漏。先让脚本出一份底稿。

```bash
python scripts/skill_conflict_scan.py <技能根目录>
python scripts/skill_conflict_scan.py <技能根目录> --only-red   # 只看确定冲突
python scripts/skill_conflict_scan.py <技能根目录> --json r.json
```

### 它怎么判（不用相似度算法）

社区里做得最好的 `skill-organizer` 明确写过一句：

> *"Do NOT use keyword matching, Jaccard similarity, or heuristic categorization."*

因为**"像不像"和"会不会抢活"是两件事**。两个技能可能描述得很像，但触发词完全不交叉，那它们不冲突。所以这里用「枚举 + 交集」，只报能举证的：

| 级 | 判据 | 能不能谈合并 |
|---|---|---|
| 🔴 **确定抢触发** | **完全相同的触发短语**被两个技能认领 | 只有这级有资格 |
| 🟡 **疑似重叠** | 共享 ≥2 个领域词，但触发短语不交叉 | 只是"值得看一眼"，多数可以不动 |
| ⚪ **名称可疑** | 名字互为子串，或带 `-v2` / `_backup` 后缀 | 先查是不是新旧并存 |

### 三条已知局限（别当成万能）

1. **不判断技能是否已关闭**。实测过读缓存不可靠（缓存里 `disable` 字段可能全是 False）。**自己对照，已关的那几组忽略**。
2. **领域词表是预定义的**。跨领域的新词（比如某个行业术语）要手动往 `DOMAIN_WORDS` 里加。
3. **只读 frontmatter**，不读正文。所以它能查"触发词打架"，查不了"指令矛盾"（一个说必须做 X、一个说绝对别做 X）——那还得靠人读。

### 拿到的报告怎么用

```
🔴 那几组 → 进 MERGE 的【判】段，做第 2–4 步
🟡 那几对 → 先放着，等 🔴 处理完再看还剩多少
⚪ 那几对 → 多半是备份目录，确认后可以清
```

⛔ **别看到红就动手合。** 红只是"确认了冲突存在"，还没判模式、没选主干、没建基线。
