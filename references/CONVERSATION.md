# 对话区：聊天记录、会话日志、工单、评论、历史 AI 对话

> **什么时候读**：进来的是**多说话人的交互记录**（聊天记录、会话日志、工单、评论、历史 AI 对话）时读。

进来的是**交互**：多说话人、带时间线、有问有答有纠正。本区动词是"筛"——噪音占八成，真规则藏在少数几句里。产物是规则条目、坑位记录、被否做法清单，每条落消息 ID。

## 1. 判定

三条同时满足才进本区：

1. 多轮交互结构：至少两个说话人（或人与 AI 的往返），带时间顺序
2. 内容含信息交换：提问、回答、纠正、争论、决策至少占一样
3. 有可引用的消息坐标：消息 ID、行号、时间戳至少占一样

### 路由边界

| 像对话但不是本区 | 去处 |
|---|---|
| 单篇文章、帖子、独白式笔记 | 文本区；没有交互结构 |
| 工单系统本身（软件）的逆向 | 软件区；工单往来内容才进本区 |
| 会议录音原件 | 先转写（视频转写工具 拿文字稿），再进本区 |
| 代码 review 邮件里的大段 diff | 主体是代码变更归代码区；评审意见归本区，分开炼 |

### 容易误判

- **独白充对话**：一个人连续发多篇（公众号连载、论坛楼主自问自答）不是对话，是文本。
- **导出格式骗人**：.html/.json 里装的可能是聊天记录。看内容结构（说话人字段、消息数组），不看扩展名。
- **AI 对话记录**：Codex CLI 的 `~/.codex/sessions/*.jsonl`、各桌面端导出，主体是历史交互，进本区；判的重点是"用户纠正过 AI 什么"。

## 2. 取料

本机现役工具：

| 工具 | 用途 | 用法 |
|---|---|---|
| Read | 读导出文件（.txt/.md/.json/.jsonl/.html） | 一次一个文件，记起止行号 |
| Grep | 捞规则化信号 | 关键词见下 |
| Glob | 列目录下全部会话文件 | `**/*.jsonl` 等 |
| PowerShell | 解析结构化导出 | `Get-Content -Raw <文件> \| ConvertFrom-Json` |

规则化信号词（Grep 第一批就搜这些）：`以后`、`默认`、`记住`、`别再`、`不要`、`改成`、`必须`、`一定`、`错误`、`坑`、`踩`、`不对`、`错了`、`为什么`。

取料纪律：

1. 原料只读不改；导出文件先落盘再处理。
2. 保留消息 ID / 时间戳 / 说话人三段元数据，它们是落点的一部分；用户名会改，ID 不会。
3. 超大对话（> 500 轮）先按话题边界切段再读，不整文件进上下文。**T2 以上要收据对账，按 [batch-processing.md](batch-processing.md) 建批次**——但对话的收据字段要换：记**话题段 ID + 覆盖的消息 ID 区间**，不是字符偏移与逐字 quote（消息 ID 是唯一稳定的，用户名和时间戳都会重复）。**本区收据是概念模板，不走 digest_batch.py 校验**——脚本只认字符区间；对账靠消息 ID 清单自查。
4. 群聊先分说话人：需求方、执行方、围观方权重不同（见第 4 节）。

## 3. 拆到什么粒度

单元 = 一个话题段：围绕同一个问题的连续轮次。一次发言（同一人连续消息合并）是最小碎片，不是判读单元。

| 原料类型 | 一级切分 | 二级切分 | 单元定义 |
|---|---|---|---|
| 群聊 / 私聊 | 日期或话题转换点 | 话题段 | 一个完整问题从提出到收口 |
| 工单往来 | 一张工单 | 一个回合 | 提问→处理→确认/驳回 |
| 会话日志 | 会话 | 话题段 | 一次任务从开始到结束 |
| 评论区 | 一帖 | 一条主评论 + 其回复 | 一个论点及其交锋 |
| AI 对话 | 一次会话 | 一轮纠正 | 用户指出问题→AI 改正→用户确认 |

硬数字：

- 单元下限 3 轮、上限 50 轮；超 50 轮按子话题切开。
- 一个单元只判一个主题；出现第二个主题就是切点。
- 预计 80% 轮次是噪音（寒暄、表情、复读、跑题），直接丢，只登记不判读。
- 第一遍只标不判：给每个单元打"含规则信号 / 纯噪音"标签；第二遍只读标了的。两遍分开，不许一遍又读又判。

## 4. 判什么

每个通过筛选的单元按序回答六问，答不出写"未知"，不许跳：

1. **说了什么**：一句可证伪的主张。写不出 = 本单元无规则，登记丢弃。
2. **什么档**：观察（原话可逐字引用）/ 推断（从多次行为归纳）/ 未知（信息不足）。三档分开，不许一段混。
3. **谁的权重**：需求方（提要求的人）> 执行方（干活的人）> 围观方。执行方的自我辩解降权；只有需求方拍板的才算规则。
4. **成立条件**：这个偏好在什么场景、对什么对象成立。"这个项目里这样"和"以后所有项目这样"是两条规则。
5. **被推翻过吗**：后续对话有没有否定它。有 = 后写覆盖先写，旧的标 DELETE 或降级为"已废弃 + 废弃原因"。
6. **落点在哪**：消息 ID / 行号 + 逐字 quote。指不回原话的整条标推断。

四类高价值信号，见到就单独标：

- **反复出现的纠正**：同一件事被说了两次以上——第一次是意见，第二次才是规则。
- **明确的规则化表达**："以后都要这样""默认走这条路""记住这个"——原话进 quote。
- **踩过的坑**：带事故、报错、失败结果的叙述——坑位记录的原料。
- **被否定的做法**：先说方案再被否——被否做法清单的原料，否的理由比方案本身更值钱。

## 4.5 二次筛选（实测：1694 条怎么降到 60 条）

信号词捞出来的量很大——实测 255 份日志命中 **1694 条**，平均每份 6.6 条。全留下等于没筛。

按三档切：

| 档 | 长什么样 | 处置 |
|---|---|---|
| **A 必留** | 含"以后 / 必须 / 禁止 / 默认 / 别再"的**祈使句** | 直接就是规则，原样搬进产物 |
| **B 合并** | 含"根因 / 坑 / 踩 / 错误 / 教训"，讲的是一个具体故障 | 同一根因的多条**合并成一条**，保留最完整的那次 |
| **C 丢弃** | 只描述状态、且对**本次目标**无增量：“已完成 X”“已修复 Y”“新增文件 Z” | 丢 |

判据一句话：**对本次目标有没有增量。** 目标不同，同一句话的归属不同：

- 目标是**提炼长期偏好 / 规则** → 能变成“下次遇到 X 就这么做”的进 A / B，纯状态描述进 C
- 目标是**事故还原 / 决策演变 / 需求变更** → **时间线与状态消息就是主干**，C 档要重新判

**留存率没有硬线。** 5–8% 只是“提炼长期偏好”场景的经验参考值；事件还原、决策演变类目标，留存率由信息增量决定，可以远高于此。**不许先定配额再丢内容。**

**合并时的取舍**：同一类坑出现 3 次以上，只保留**最新那次**（前面的可能已被后续修复推翻）+ 一句话说明它复发过。

## 5. 装成什么

**产出形态由目标决定**：偏好 / 规则类目标 → 规则条目为主，剧情概括一律不产；**事件还原 / 决策演变类目标 → 时间线是主干**，状态与决策做节点。先问目标，再定形态。

**模板 A：规则条目卡**

```json
{"id":"conv-rule-<短名>-<n>","rule":"祈使句，一步一动","said_by":"需求方","quote":"逐字原话","applies_when":["条件"],"void_when":["条件"],"op":"ADD|UPDATE|DELETE|NOOP","kind":"fact|inference|unknown","evidence":[{"msg_id":"","quote":""}]}
```

**模板 B：坑位记录**

```json
{"id":"pitfall-<短名>-<n>","incident":"出了什么事","root_cause":"根因一句话","trigger":"什么条件下复现","prevention":"预防动作，动词开头","evidence":[{"msg_id":"","quote":""}]}
```

**模板 C：被否做法清单**

```json
{"id":"rejected-<短名>-<n>","approach":"被否的做法","rejected_because":"否的理由，逐字优先","rejected_by":"谁否的","instead":"替代方案，无则 null","evidence":[{"msg_id":"","quote":""}]}
```

入库纪律（借 Mem0 的做法）：每条抽取结果先与库里已有条目比对，再决定 `ADD`（全新）/ `UPDATE`（补充或修正旧条）/ `DELETE`（被后续对话推翻）/ `NOOP`（已有等价条目）。无脑追加 = 不合格，同一件事在库里只存在一条。

## 6. 量化标准

| 指标 | 达标线 | 核法 |
|---|---|---|
| 四态齐标 | 每条结论带 ADD/UPDATE/DELETE/NOOP 之一 | 逐条查 op 字段 |
| 库内重复率 | 0（同一事实只存一条） | 按 rule 文本相似度对账 |
| 落点率 | ≥ 80% 条目能指回消息 ID + 逐字 quote | 其余必须标推断 |
| 保留率 | **由目标定**：偏好提炼参考 ≤20%；事件还原 / 决策演变不设上限，按增量留 | 偏好场景高于此回第 3 节；还原场景看增量 |
| 单条目体量 | ≤ 5 行（参考值，时间线节点可放宽） | 超了先想拆不拆 |
| 摘要产出 | **偏好类目标 0 条**；还原类目标时间线是主干、不算摘要 | 产物里出现无增量的剧情复述才不合格 |

## 7. 失败模式

| 失败 | 症状 | 正解 |
|---|---|---|
| 摘要冒充炼化 | 产物是一段剧情复述，下一步拿不走任何东西 | 只产规则条目/坑位/被否清单；复述一律不写 |
| 同一件事存十遍 | 库里五条规则说的是一个偏好 | 入库前比对，标 ADD/UPDATE/DELETE/NOOP；重复率对账 |
| 气话当规则 | "我要卸载这破工具"进了规则库 | 规则化信号词 + 需求方权重双条件；情绪单元直接丢 |
| 新旧规则并存 | 早期偏好和后期纠正矛盾，两条都在库里 | 按时间线后写覆盖先写；旧的标 DELETE 或降级废弃 |
| 讨论当承诺 | 闲聊里提过的方案被升级成正式规则 | 只有带"以后/默认/必须"信号的才升级；其余是方案素材，分开堆 |
| 长对话一次吞 | 500 轮整文件进上下文，读到后半忘了前半 | > 500 轮先按话题切段；段间只传结论不传原文 |

## 8. 交付前自检（三条，逐条打勾）

- [ ] 产物里有没有**剧情复述**？（有就没炼成，只是换了个说法的摘要）
- [ ] 每条规则能指回**消息 ID** 吗？
- [ ] 新旧矛盾是**按时间线覆盖**了，还是两条并存？

对话区最常见的自欺是我读完了——读完不等于炼成。
