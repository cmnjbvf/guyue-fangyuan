# 痕迹总纲：任何东西，先看它在电脑上留下了什么

**这份文件解决什么**：你说不清的那个"宏观大能力"，学界有正式名字——**数字取证与事件响应（DFIR）**，有 NIST 国际标准（SP 800-86）。它要回答的问题和你想要的一模一样：

> **一个东西我没见过、没有源码、甚至它已经不在了，我能不能仅凭它留下的痕迹，把它完整重建出来？**

**核心立论（比"载体分类"更底层一层）**：

> **你拆不了"东西"，你只能拆"数据"。**
> 任何东西在电脑上的存在形式，只有**五类**，没有第六类。
> 所以"宇宙万物"这件事，是可以收敛的。

**三层结构（这是整套东西的骨架）**：

```
任何东西  →  归到五类数据源  →  按 NIST 四阶段采集与检查  →  五维提取（TAKE.md）  →  变成我的
             ↑ 本文件管这里                                    ↑ 那份文件管这里
```

---

## 一 · 五类数据源（"宇宙万物"的收敛）

NIST SP 800-86 原本分四类（Files / OS Data / Network / Application），本项目把**内存**单列——因为它易失性最高、信息量最大、最容易被错过。

| # | 数据源 | 典型载体 | 取证入口 | 能回答什么 | 易失性 |
|---|---|---|---|---|---|
| **1** | **文件** | 文档 / 图片 / 可执行 / 配置 / 数据库 | 文件系统、哈希、签名、carving | 它**是什么**、**有没有被改过** | 低（磁盘上，删了还能捞） |
| **2** | **系统数据** | 注册表 / 事件日志 / 用户账户 / 计划任务 / 已装软件 | 注册表 hive、EventLog、Prefetch | 它**什么时候运行过**、**谁动过** | 中 |
| **3** | **应用数据** | 浏览器历史 / 聊天记录 / 邮件 / 应用日志 / leveldb / sqlite | 各应用自己的存储 | 它**被谁用过**、**用来干什么** | 中 |
| **4** | **网络流量** | pcap / HAR / flow / 防火墙日志 / DNS 查询 | 抓包、代理日志、HAR | 它**跟谁通信**、**协议长什么样** | **高**（不提前抓就没了） |
| **5** | **内存 / 运行时** | 进程内存 / core dump / 运行时对象 | dump、调试器、进程枚举 | 它**此刻在干什么**、**密钥是什么** | **最高**（关机就没） |

**判据**：拿到一个东西，先问「**它在哪一类里留下了痕迹**」，而不是先问「它是什么软件」。

**一个东西常常横跨好几类**：一款 App 会同时留下文件（APK 本体）、系统数据（安装记录）、应用数据（聊天库）、网络流量（API 调用）、内存（运行时密钥）。**跨类的部分要单独去捞，不要指望一网打尽。**

## 二 · 易失性顺序（先抓什么，RFC 3227）

**这是唯一一条"顺序错了就没救"的规则。** 抓取证材料必须从最易失的开始：

```
① 内存（进程、连接、密钥）      ← 关机就没了
② 网络连接与路由表              ← 断开就没了
③ 运行中的进程与句柄
④ 磁盘上的文件与元数据          ← 删了还有机会捞
⑤ 日志（远端 syslog、云日志）    ← 有保留期
⑥ 备份 / 归档 / 快照            ← 最持久
```

**落到日常**：让一个东西"变成我的"之前，先看它现在**还在不在跑**。
- 正在跑 → **先 dump 内存和连接**，再去看磁盘。顺序反了，运行时的东西就永久丢失。
- 已经不在 → 直接进磁盘与日志。

## 三 · 正向与逆向：两条追踪路线（你说的"正向搜索/逆向搜索"）

这不是两种搜索技巧，是**时间线上的两个方向**，而以**锚点**为轴：

```
        ← 逆向（向后推：它是怎么来的）
锚点 ────────────────────────────────
        → 正向（向前推：它后来干了什么）
```

| 方向 | 起点 | 问什么 | 典型产出 |
|---|---|---|---|
| **逆向** | 一个确定的事实（第一次告警、一个哈希、一条消息） | **它是怎么来的？** 初始入口在哪？谁先碰的它？ | 来源链、首次出现时间、上游依赖 |
| **正向** | 同上 | **它后来干了什么？** 影响了谁？扩散到哪？ | 影响面、后续动作、衍生文件 |

**权威做法（DFIR 标准流程）**：
1. 先确立**锚点**——一个时间确定、来源可靠的事件；
2. 从锚点**向后推**，找最初的进入点；
3. 从锚点**向前推**，找后续活动；
4. **找时间线里的空洞**——空洞往往意味着日志被清或痕迹被删（**这本身就是信息**）。

**落到"变成我的"**：
- 逆向 = 这个东西的**设计来源**（它抄了谁、解决了什么老问题）
- 正向 = 这个东西的**影响面**（谁在用它、它改了什么行业惯例）
- **你要的"机制"，在逆向那半边；你要的"值不值得抄"，在正向那半边。**

## 四 · 单源不可信：三源收敛原则

**任何一条痕迹单独看都可能被骗。要三个独立来源指向同一个结论，才算事实。**

DFIR 里最经典的例子——**判断一个文件的时间戳有没有被伪造**：

| 来源 | 谁写的 | 可信度 |
|---|---|---|
| `$STANDARD_INFORMATION` 时间戳 | **用户态可改**，篡改工具专攻这里 | 低（对手可编辑） |
| `$FILE_NAME` 时间戳（在 MFT 里） | **内核写**，不改内核动不了 | 高 |
| `$LogFile` 的 LSN 记录 | NTFS 驱动每次写 `$SI` 都留一条 | 高（记录"什么时候写的"，与"写的什么值"独立） |

**三者一致 → 铁证；`$SI` 与 `$LogFile` 记录的写入时间矛盾 → 不是"异常"，是"确有篡改"。**

**这条原则能直接搬到"拆东西"上**：
- 一个 App 说自己"不联网"？→ 看它的**网络流量**（第四条源）对不对得上
- 一段代码看起来"没做某事"？→ 看它的**依赖**和**运行时**有没有偷偷做
- 文档说"架构是这样"？→ 拿**代码**核，文档只是二手

**别用单一来源下结论——这是 `TAKE.md` 五维里"证据强度"的底层理由。**

## 五 · 元数据 vs 指纹：两种溯源，后者撕不掉

这是整套方法论里最深刻的一对区分：

| | 元数据溯源（标签） | 内容溯源（指纹） |
|---|---|---|
| 是什么 | 文件里**主动写进去**的说明（EXIF、C2PA、作者、创建时间） | 从**内容本身**读出的特征（传感器噪声、压缩指纹、统计分布） |
| 强度 | 存在时很强，**但一撕就没** | **撕不掉**，因为它不是附加的 |
| 弱在哪 | 社交平台上传即剥离、转码即丢失、截图等于新建文件 | **概率性**，只能给置信度，不能给绝对判断 |
| 类比 | 包裹上的**快递单** | 包裹上的**指纹** |

**为什么重要**：大多数"溯源"工作停在第一层，于是"元数据被剥了"就宣布查不下去。**第二层才是真正查得下去的那层。**

**落到"变成我的"**：
- 你从教程/书里抄来的方法论 = 元数据（作者说他是怎么想的）
- 你从他**实际行为**（作品、代码、决策记录）反推出来的 = 指纹
- **前者可能是包装过的说辞，后者骗不了人。**

## 六 · Windows 痕迹速查表（本机可直接用）

**这一节是"任何东西在 Windows 上留下什么"的实操清单。**

| 痕迹 | 位置 | 能证明什么 | 关键细节 |
|---|---|---|---|
| **Prefetch** | `C:\Windows\Prefetch\*.pf` | **一个 exe 运行过** | 含运行次数、最后运行时间、访问过的文件；**exe 被删了它还在** |
| **Amcache** | `Amcache.hve` | 最近运行过的程序 + **SHA-1** | **删了文件也能把哈希和运行关联起来** |
| **Shimcache** | `AppCompatCache`（注册表） | 文件**存在过**（不证明运行） | 只能证明"在磁盘上出现过" |
| **LNK / Jump List** | 用户目录 | 最近**打开过哪些文档** | 能还原"打开过什么、从哪打开的" |
| **`$MFT`** | NTFS 主文件表 | 每个文件的**四个时间戳**（创建/修改/访问/MFT变更） | 删了文件的记录**保留到记录被复用** |
| **USN Journal** | `$UsnJrnl` | **创建/改名/删除的完整序列** | 还原"文件是怎么一步步没的" |
| **`$LogFile`** | NTFS 事务日志 | **元数据写入的时间**（与写入的值独立） | 用来验时间戳有没有被改 |
| **事件日志** | `System32\winevt\Logs` | 登录、服务、驱动、审计 | 时间线的骨架 |
| **USBSTOR** | 注册表 | 插过**哪些优盘/手机**（含序列号） | 和文件修改时间关起来就能对上 |
| **Shellbags** | 注册表 | 用户**浏览过哪些文件夹**（即使盘已拔） | 证明"他看过这里" |
| **浏览器数据** | `AppData\...\User Data\Default` | 历史、下载、**本地存储 leveldb** | 网页应用的"应用数据"都在这 |
| **回收站 `$I*`** | `C:\$Recycle.Bin` | **被删文件的原路径**（UTF-16） | `$I` 存路径，`$R` 存内容 |
| **`$LogFile` / VSS 快照** | 卷影副本 | **删除前的状态** | 恢复"删掉之前长什么样" |

**一句能记住的**：
> **exe 被删了，Prefetch 还记得它跑过几次；文件被删了，MFT 还记得它存在过；记录被清了，USN 日志的空洞本身也是证据。**

## 七之一 · 极限速度：怎么做到"又详细又快"

### 先认清矛盾在哪

**"详细"和"快"不是同一个维度的事。** 详细的真实瓶颈有三个，**没有一个是"执行慢"**：

1. **每次都从头想** —— 没有固定框架，每次都在重新设计怎么拆
2. **把所有细节塞进对话** —— 上下文一满，前面拆的全作废，等于白干
3. **在垃圾上花时间** —— 拆了一个根本不值得拆的东西

所以提速的方向不是"跑得更快"，是**消除这三种浪费**。

### 六个手段（按实测收益排序）

| # | 手段 | 收益 | 怎么做 |
|---|---|---|---|
| **1** | **分级拆解** | **最大** | 见下表。核心：不是每个部件都配得上精拆 |
| **2** | **第 0 关跳过** | 巨大 | 先判"值不值得拆"，不值得就停。**不做事比做快更省时间** |
| **3** | **落盘不落对话** | 巨大 | 详细产物写文件，对话里只留索引。否则上下文满了，前面全丢 |
| **4** | **脚本替模型** | 快百倍 | 哈希、字符串、文件清单、时间戳排序 → 全用脚本。**只有"判断"才用模型** |
| **5** | **并行** | 3–5 倍 | 不同部件 / 不同数据源分给子代理。**但派活必须写全路径和验收标准**（子代理看不到主对话） |
| **6** | **缓存** | 省重复 | 同一个东西按**哈希**缓存拆解结果，下次直接引用 |

### 分级拆解（解决"又详细又快"的唯一办法）

**像考古：先探地雷达扫一遍，再决定挖哪。**

| 档 | 花多久 | 做到什么程度 | 产出 | 什么时候停 |
|---|---|---|---|---|
| **L1 侦察** | 分钟级 | 只看结构 + 入口 + 契约。**不读实现** | 一句话结论：「这东西值不值得深挖」 | 判断出"不值得"就停 |
| **L2 骨架** | 小时级 | 五维全提，但每个部件只到"**能描述**" | 机制规格书（骨架版） | 能画完数据流和决策规则表就停 |
| **L3 精拆** | 按需 | 只对**关键部件**做到"**能重写**" | 该部件的可执行规格 | 能照着写出等效实现就停 |

**铁律：不是每个部件都配得上 L3。**
一个 App 可能有 200 个类，真正决定它"是什么"的可能只有 15 个。**把 L3 花在那 15 个上，剩下的用 L2 描述即可。**

**判据**：这个部件**换掉之后，用户能不能感觉到差别？** 感觉不到 → 停在 L2。

### 详尽的产物必须落盘（这条最容易被忽略）

```
对话里只留：索引 + 结论 + 下一步
文件里才放：完整的机制规格书、决策规则表、失败模式清单
```

**理由**：对话上下文有硬上限。你把 300 行拆解结果塞进对话，第 200 行时前面的就已经开始被挤掉了。**写进文件的东西不会消失，留在对话里的会。**

这也是本技能整套设计的底层原因：**总地图 + 按需读手册**，而不是"一次读全部"。

### GitHub API 限额的绕法（实测）

| 限额 | 数字 | 绕法 |
|---|---|---|
| 未认证 API | **60 次/小时** | ① 配 `GITHUB_TOKEN` 提到 5000/小时；② **根本不调 API**——release 下载 URL 有固定规律 `releases/download/v<版本>/<文件名>`，知道版本号就能直接拼；③ 用镜像站 |
| search API | 10 次/分钟 | 用普通搜索代替，或错峰 |
| 下载走代理 | 时好时坏（实测 0–1.6 MB/s） | **国内镜像优先**：清华 TUNA 实测 **8.4 MB/s** |
| 有反爬的站 | Turnstile 验证 | 只能人工看，或换数据源 |

**实测提醒**：今天为了查三个工具的版本号，各调了一次 releases API，**60 次配额直接吃掉 41 次**。→ **能拼 URL 就别调 API。**

## 七 · 这跟"拆解蒸馏"怎么接

**接在三个地方：**

| 环节 | 本文件给什么 | 接到哪 |
|---|---|---|
| **判入口** | 五类数据源（先去哪捞） | 比 `00-map.md` 的五区更底层：**先判数据源，再判载体** |
| **定顺序** | 易失性顺序（先 dump 还是先读盘） | 防"顺序错导致证据永久丢失" |
| **判真伪** | 三源收敛 + 元数据/指纹之分 | 支撑 `TAKE.md` 五维里"证据强度不许超过结论强度" |

**完整链路**（把三份文件串起来）：

```
① 这东西在电脑上留下了什么？        → 本文件（五类数据源）
② 按什么顺序、用什么手法捞？        → 本文件（易失性顺序 + 速查表）
③ 捞到的东西怎么拆成机制？          → TAKE.md（五维提取）
④ 拆出来的机制怎么变成我的产品？    → TAKE.md（四层融合 + 重建次序）
⑤ 几个东西要合成一个怎么办？        → MERGE.md（合并与验证）
```

## 八 · 本机能力边界

| 能力 | 状态 |
|---|---|
| 读文件系统元数据（时间戳、大小、属性） | ✅ python / PowerShell 都能做 |
| 解析 APK / 二进制 | ✅ REA MCP + apktool + jadx（见 `TAKE.md` 八） |
| 读注册表 hive | ⚠️ 需要解析器（python `regipy`，未装）；在线可查 HKCU/HKLM |
| 解析 `$MFT` / USN Journal | ❌ 需要 MFTECmd（Windows 版）或 dfir_ntfs（python），未装 |
| Prefetch 解析 | ❌ 需要 PECmd，未装 |
| 事件日志 | ⚠️ `Get-WinEvent` 可用（PowerShell），深度解析需工具 |
| 抓包 | ⚠️ 需 Wireshark / tcpdump；`SOFTWARE.md` 有 HAR 分析入口 |
| 内存 dump | ❌ 需专用工具（WinPmem 等），未装 |
| 时间线合并（plaso） | ❌ 未装（Linux 工具） |

**现状判断**：**"文件 + 应用数据"这两类现在能做得很扎实；"系统数据"要装 2–3 个解析器；"网络"和"内存"暂时做不了。**

**不要因为后两类做不了就说整条路不通**——按本节第二段，前两类已经覆盖了大多数"拆一个东西"的需求。

## 九 · 授权边界（取证的前提，不是客套）

DFIR 的第一条纪律是**确认授权**。搬到这里同样成立：

- **只分析你有权分析的东西**：自己的设备、自己买的软件、明确允许逆向的协议、公开可获取的材料
- **别人的设备、别人的账号数据、公司内网留痕** → 需要明确授权，否则不是技术问题而是法律问题
- **不在原件上动手**：永远操作副本，原件保持可追溯（对应 `TAKE.md` 的"只拿机制不拿代码"）
